# 1. C++ API 设计

Martin Reddy《API Design for C++》原则的开发落地：公共符号是对客户的长期承诺；实现可换，已发布契约很难收回。

> 来源：Martin Reddy《API Design for C++》（图灵中文版，刘晓娜 / 臧秀涛 / 林健 译，人民邮电出版社，2013）。扫描 PDF 共 379 页。本文是原书原则的压缩与讲解，不是全书摘录。示例为说明原理而重写。

## 【核心精简提纲】

### 记忆主干

**公共符号是承诺 · 头文件是产品 · 隐藏细节（Pimpl / 前向声明 / 禁止头文件平台宏）· 核心小、便捷另包 · const / explicit / 命名空间 · 签名写清所有权与错误 · 不为性能扭曲抽象 · 发版后只演进不改契约 · 文档 + 契约测试 · 默认拒绝单例 / friend / 公共 `#define` / 抽象基类乱加纯虚**

日常 90% 的决策落在优质特征、分析→设计→实现、头文件纪律、版本兼容。写公共头文件、做接口评审、准备发版时，先过提纲区检查清单。

### 核心要点清单

- API 应对问题域做准确抽象；好 API 的首要目标是新版本对客户代码影响最小
- 物理隐藏 + 逻辑隐藏；公共头文件禁止平台 `#if`、内部类型、实现 `#define`
- 最小完备：不确定要不要的接口不要提供；虚函数也是继承契约
- 易用：可发现、不易误用、命名/参数顺序/错误策略全库一致
- 正交与资源安全：RAII / `unique_ptr`；松耦合、高内聚
- 跨 `.so`/`.dll` 用纯 C 或 C++ + Pimpl；模板不要直接做成稳定 ABI 边界
- 只加不改 → 次版本；改行为/布局/删符号/加纯虚 → 主版本

### 1. 这本书在解决什么问题

C++ 实现可以改，**已经发布的接口很难改**。接口一变，所有依赖方都要改代码、重编、重测；实现一变，客户端往往无感。因此：

- 你写给别人（或未来的自己）调用的头文件、ABI、协议、脚本绑定，都是 API。
- 好 API 的首要目标：在提供所需功能的前提下，**新版本对客户代码的影响最小，理想是零影响**。
- 本书覆盖完整生命周期：建模 → 设计 → C++ 落地 → 性能 → 版本 → 文档 → 测试 → 脚本绑定 → 可扩展，而不是只讲语法技巧。

**对开发的直接含义：** 把「公共接口」当成产品来设计，而不是实现的副产品。先想契约，再写代码。

术语约定（与原书一致，开发时也建议统一）：

| 术语 | 含义 |
|------|------|
| 用户 / 客户 | 调用你 API 的程序员或程序，不是最终产品用户 |
| 模块 / 组件 | 一对 `.h` + `.cpp`，一个组件可含多个类 |
| 库 | 多个模块打成的物理包 |
| 方法 | 成员函数（书中与 method 混用） |

### 2. 全书主线（开发时怎么串起来）

```text
问题域建模（抽象要对）
    → 优质接口的特征（第2章：隐藏、最小、易用、正交、松耦合、稳定）
    → 用对模式（第3章：Pimpl / 工厂 / 包装 / 观察者；单例慎用）
    → 分析→设计→实现（第4章：架构 / 类 / 函数）
    → 选定风格（第5章：纯C / OOP / 模板 / 数据驱动）
    → C++ 用法把关（第6章）
    → 接口性能，而不是扭曲设计换速度（第7章）
    → 发版后只能演进不能改契约（第8章）
    → 文档补全行为（第9章）
    → 自动化测试守住不破坏客户（第10章）
    → 需要时再脚本化 / 插件化（第11–12章）
```

日常开发 90% 的决策落在 **第 2、4、6、8 章**。其余章节按需查阅。

### 3. 优质 API 的六项特征（第 2 章）

这是全书最重要的一章。写任何公共符号前，用这六条自检。

#### 3.1 问题域建模：给逻辑抽象，不给实现细节

- API 应对问题域做**准确抽象**，暴露领域对象和操作，而不是文件格式、压缩算法、平台调用。
- 模型会随需求变。新增需求时要**重新评估对象模型**，但不要过度通用（「比需求更通用」往往变成无法维护的框架）。
- 自检：把头文件给非该模块作者看，他能否讲清「这套接口在干什么」。

#### 3.2 隐藏实现细节（信息隐藏）

这是做 API 的**第一原因**：实现可换，客户不受伤。

- **物理隐藏**：客户拿不到实现源码；头文件只有声明。
- **逻辑隐藏**：用语言机制禁止访问（`private`、不完整类型、不把内部类型放进公共头文件）。
- 声明与定义分离：公共头文件只告诉编译器名字和类型，不分配对象布局细节（Pimpl 把布局完全移出头文件）。

开发落地：

- 公共头文件禁止出现平台 `#if` / `#ifdef`（那是在公开实现差异，并让 API 因平台而异）。
- 内部类型、内部头文件不要被客户 `#include`。
- 能放 `.cpp` 的常量、默认值、依赖，就不要出现在 `.h`。

#### 3.3 最小完备：简洁，但不过度简洁

- **完备**：客户需要的能力都有（靠需求 / 用例收集，而不是猜）。
- **最小**：每个公共符号都是一项**生命周期承诺**——加上容易，删掉会逼客户改代码或弃用你。
- 奥卡姆剃刀：**若无必要，勿增实体。不确定要不要的接口，就不要提供。**
- 虚函数也是承诺：每加一个 `virtual`，就多锁定一份继承契约。
- 「便捷 API」不要污染核心：核心保持小而稳，便捷层做成独立模块（书中用 OpenGL / GLU / GLUT 分层说明）。这叫**渐进公开**（progressive disclosure）。

#### 3.4 易用：最小惊奇

- 简单任务应该一眼会用，最好从函数签名就能读出用法。
- 一致的命名、参数顺序、错误策略；示例代码比长篇说明更有效。
- 可发现、不易误用、行为一致。专家功能可以有，但不要挡在主路径上。

#### 3.5 正交与资源安全

正交两点：

1. **少冗余**：同一信息只有一个权威来源。
2. **增独立**：概念不重叠；一组算法应能套到多种容器（像 STL 算法与容器分离）。

资源：C++ 没有 GC，接口必须让所有权清晰，避免空指针解引用、二次释放、new/delete 混用、数组 `delete` 错误、泄漏。开发时优先：

- RAII / 智能指针（共享、弱、作用域）。
- 工厂返回的所有权在签名里写死（`unique_ptr` 比裸指针更不易误用）。

#### 3.6 松耦合、高内聚

- 耦合：组件之间互相依赖的强度。
- 内聚：组件内部是否围绕同一职责。

度量耦合时可看：连接数量、可见度（全局量很糟）、密切度（继承通常比组合更紧）、改签名时波及面、有没有循环依赖。

目标：**改 A 时，B 尽量不用改。**

#### 3.7 稳定、有文档、可测试

稳定 ≠ 永不改变，而是：

- 接口版本化；
- 升级保持向后兼容；
- 设计为可扩展（演进，而不是推倒重来）；
- 文档写清行为、错误、最佳实践；
- 自动化测试保证新变更不破坏旧用例。

### 4. 设计流程：分析 → 设计 → 实现（第 4 章）

```text
分析（需求 / 用例 / 用户故事）
    → 设计（架构 / 类 / 函数）
    → 实现（编码 / 测试 / 文档）
         ↑ 新需求或缺陷会回到分析和设计
```

要点：

- 敏捷过程**不会替你设计 API**。有了用户故事，仍需要独立的设计步骤。
- 好设计是持续过程，不是第一步做完就结束。技术债要还，长期项目尤其要从一开始就为演进留空间。
- 先做**对象层次结构**（整体架构：part-of），再做**类层次结构**（is-a），再落到函数签名。

#### 4.1 架构

- 识别主要抽象，创造关键对象，选架构风格。
- 架构文档要写**高层结构 + 原理**（为什么选这个、放弃了什么），否则后人会觉得接口难学。
- 发版前做设计审查：架构师、实现者、客户一起看。

#### 4.2 类设计

- 一个类只做一件事并做好（名字应直接传达意图；含糊缩写是坏味道）。
- 接口类可用形容词（`Renderable`）或 `I` 前缀；全库用命名空间或统一前缀防冲突。
- 遵守：
  - **Liskov 替换**：子类必须能替换基类而不破坏客户假设。
  - **开放-封闭**：对扩展开放，对修改封闭。
  - **迪米特法则**：只与直接朋友说话，不要链式掏内部对象。
- 继承是强耦合。默认用组合；只有「为了被继承而设计」的基类才提供虚析构和稳定虚接口。

#### 4.3 函数设计（每次加公共函数都要做的选择）

自由函数：静态与否、值/引用/指针、const、默认参数、返回方式、操作符、异常规格。  
成员函数再加：虚/非虚、纯虚/非纯虚。

命名：动词清晰；参数顺序全库一致（例如总是 `handle, options`）；一对互补操作命名对称（`Add`/`Remove`，不要混用 `Delete`/`Erase`）。

错误处理全库只能选一种主策略并写进文档：返回码、异常、或 `std::expected` 一类。不要同一层混用三种。

### 5. 四种 API 风格，怎么选（第 5 章）

同一功能可以用完全不同的调用方式。书中用 FMOD 对比三种风格。选型建议：

| 风格 | 形态 | 适合 | 代价 |
|------|------|------|------|
| 纯 C | 自由函数 + 结构体 + 句柄，无对象/继承 | ABI 稳定、跨语言、嵌入式、插件边界 | 无封装；靠前缀防冲突；所有权靠约定 |
| C++ 面向对象 | 类、封装、继承、多态 | 领域对象清晰、同一进程 C++ 客户 | ABI 易碎（布局、虚表）；需要 Pimpl 才能稳二进制 |
| 模板 | 泛型与特化 | 零开销抽象、静态多态、策略类 | 编译慢；错误难读；隐式实例化会把实现暴露进头文件 |
| 数据驱动 | 打包参数/命令发给处理程序 | 脚本、RPC、可扩展命令、向前兼容 | 类型弱；调试难；不适合热路径上的细粒度调用 |

实践组合（很常见）：

- **稳定边界用纯 C 或 Pimpl 类**；
- **内部用 C++ 对象模型**；
- **需要客户扩展算法时用模板策略或插件**；
- **需要加字段而不改函数签名时用数据驱动**（书中指出：可变参数列表天生更「向前兼容」）。

### 6. C++ 落地：公共头文件纪律（第 6 章）

这是每天写代码时最该遵守的一章。

#### 6.1 命名空间

- 始终给公共符号加 **namespace 或统一前缀**。
- **禁止**在公共头文件的全局作用域写 `using namespace xxx;`（会污染客户全局符号，毁掉命名空间的意义）。
- 客户头文件里引用别的命名空间时写全名，如 `std::string`。
- 内部细节可放 `detail` 嵌套命名空间，并明确「客户不要依赖」。

#### 6.2 构造、赋值、explicit

编译器可能生成：默认构造、析构、拷贝构造、拷贝赋值（C++11 之后还有移动）。有资源的类必须显式定义或删除这一组（Rule of Three/Five/Zero）。

- **单参数构造函数加 `explicit`**，避免意外隐式转换把类型安全打穿。
- 转换操作符同样考虑 `explicit`。
- 若类不可拷贝，显式 `= delete`，不要依赖「忘了写」。

#### 6.3 const 正确性（必须贯穿公共 API）

- 不修改 `*this` 的成员函数标 `const`：这既是文档，也让客户能在 `const` 对象上调用。
- 不修改的参数用 `const T&` / `const T*`。
- 返回值该不该 `const` 要想清楚（避免无意义的 `const` 值返回妨碍移动）。

#### 6.4 模板

- 决定 **隐式实例化**（实现进头文件，客户任意类型都能用，但暴露实现、拖慢编译）还是 **显式实例化**（实现藏在 `.cpp`，只支持你列出的类型，二进制更稳）。
- 对外 API 若要 ABI 稳定，不要把重模板接口直接做成跨 .so/.dll 边界。

#### 6.5 操作符重载

- 只重载含义与内建类型一致的操作（`+` 不要做成 `LaunchMissile`）。
- 对称运算（`==`、`+`）优先非成员；修改自身的（`+=`、`[]`）做成员。
- 能不用操作符就用命名函数，尤其是团队里 C 背景客户多时。

#### 6.6 参数传递

| 意图 | 推荐 |
|------|------|
| 只读、非空对象 | `const T&` |
| 只读、可空 | `const T*` |
| 输出 / 可选输出 | 指针（空表示「不要这个输出」），或返回值 |
| 转移所有权 | `T` 按值（可移动）或 `unique_ptr<T>` |
| 共享所有权 | `shared_ptr<T>`（明确这是共享，不要随手上） |
| 内建小类型 | 按值（`int`/`bool`/`float` 不要 `const int&`） |

默认参数：若默认值是实现里的魔法数字，**用重载代替默认参数**，把默认值藏进 `.cpp`，以后才能改默认而不破坏 ABI。  
`NULL` / `""` 这类「哨兵默认」可以留在签名上。

#### 6.7 不要用 `#define` 做公共常量

`#define` 无作用域、无类型、会泄漏实现。公共 API 用 `const`、`constexpr`、`enum` / `enum class`。  
宏如果必须用，只留在 `.cpp` 或内部头文件。

#### 6.8 避免 friend 穿透封装

`friend` 会把内部实现绑死在另一个类上，测试和「方便访问」都不是给客户 API 开后门的理由。测试优先测公共行为；非要测内部，用测试专用构建或内部测试夹具，不要把 friend 写进发布头文件。

#### 6.9 导出与编码规范

- DLL/so 要有明确的导出宏；不要默认导出一切。
- 全库统一：类/函数命名风格、成员前缀（书中示例：数据成员 `m`、静态 `s`）。一致性本身就是易用性。
- 每个头文件：include guard（或 `#pragma once`）、必要 `#include`、一个命名空间。

### 7. 模式：该用哪些，不该滥用哪些（第 3 章）

原书不讲完 GoF，只抓对 C++ API **真正关键**的几项。

#### 7.1 Pimpl（强烈建议成为习惯）

把私有数据和方法挪到 `.cpp` 里的 `Impl`，公共类只留一个指向 Impl 的指针。

收益：

- 头文件干净，客户读到的就是真正的公共接口；
- 客户无法靠 `#define private public` 一类手段掏内部；
- 公共头不再 `#include` 实现依赖，**降耦合、加快客户编译**；
- 对象公共布局只是一个指针，**改实现往往不影响二进制布局**。

代价：多一次堆分配和间接访问。热路径上的极小对象可以不用；一旦类会跨库发版，优先 Pimpl。

必须处理复制语义：用智能指针管 `Impl`；要深拷贝就自己写拷贝构造/赋值，不要让浅拷贝导致双重删除。

#### 7.2 工厂

构造函数不能返回失败、不能虚、不能返回基类指针、名字被钉死。需要「创建时还不想暴露具体类型」时用工厂。

- 返回接口指针 / `unique_ptr<Base>`；
- 扩展工厂时加新的创建函数或注册表，而不是让客户 `new Concrete`。

#### 7.3 包装：代理 / 适配器 / 外观

用来包遗留接口、统一子系统、做一对一转发。写新 API 时很常见的一步是：**先不要改旧实现，在外面加一层干净外观。**

#### 7.4 观察者

解耦「状态变化」和「谁需要知道」。注意推模型 vs 拉模型、回调生命周期、以及不要在通知里重入修改订阅列表。

#### 7.5 单例：默认不选

单例只是更体面的全局变量。它引入全局状态、破坏可测性、日后很难变成「每会话一个实例」。

替代：依赖注入、把状态放到会话/上下文对象、或「工具箱单例」只包真正全局的东西（系统剪贴板），领域对象不要做成单例。

问自己：将来会不会需要两个实例？若可能，现在就不要做成单例。

### 8. 性能：不要扭曲 API 换速度（第 7 章）

核心观点：

1. **实现可以以后优化，接口很难事后优化。** 第一版就可以把调用开销、所有权和拷贝语义设计对。
2. **不要为性能扭曲问题域抽象。** 先正确，再量测，再优化实现。
3. 用真实负载的剖析数据找瓶颈（Amdahl：优化只占 1% 时间的路径，整体几乎不变）。

接口层就能做、且通常不伤害设计的优化：

- 只读对象用 `const T&`，避免拷贝构造整棵对象树（嵌入式栈空间尤其敏感）。
- 最小化公共头文件的 `#include`：前向声明、去掉「无所不包」的总头、Pimpl 把依赖推进 `.cpp`。
- 常量用真正的常量，让编译器参与。
- 用初始化列表，避免先默认构造再赋值。
- **不要为了「可能快一点」把大量函数塞进头文件当 inline**——会拖垮客户编译，且让实现无法改。
- 提供迭代器 / 连续存储访问，避免强迫客户走最慢的路径；但先提供正确抽象，再补快路径。
- 关注五类性能：编译时间、调用耗时、内存、库体积、启动/加载时间。

### 9. 版本与兼容性（第 8 章）——发版后的第一原则

**API 发布后可以演进（evolve），不应改变（change）已发布契约。**

#### 9.1 版本号

典型 `主.次.补丁`：

- **主版本**：不兼容变更（删接口、改行为、破 ABI）。
- **次版本**：向后兼容的新功能。
- **补丁**：修 bug，不改接口。

客户必须能查询库版本。提供编译期宏和运行时查询函数。

#### 9.2 兼容性分层（承诺要写进发版说明）

| 类型 | 含义 | 常见破坏者 |
|------|------|------------|
| 功能兼容 | 旧程序换新库仍完成同样任务 | 静默改变默认行为、精度、错误码 |
| 源代码兼容 | 旧代码不改即可用新头文件重编 | 改签名、改默认参数、给抽象基类加纯虚函数 |
| 二进制兼容 | 旧客户二进制不重编也能链新库 | 改对象布局、虚表、调用约定、导出符号 |
| 向前兼容 | 新客户代码能在旧库上降级运行 | 新必选参数、新必选虚函数 |
| 协议/文件兼容 | 新旧进程、新旧文件能互读 | 改包格式却不升版本字段 |

#### 9.3 维护向后兼容的手法

**安全：加。** 新类、新自由函数、新非虚方法，一般不破坏旧客户。

**危险：**

- 给客户必须实现的抽象基类**新增纯虚函数**（旧派生类变抽象，无法编译）。应变通：新方法带默认空实现，或新接口拆成新基类。
- 改虚函数顺序/签名（破 ABI）。
- 在公共类里加非静态数据成员（改对象大小）。Pimpl 可避免。
- 改 `enum` 数值、改默认参数值（源码兼容但行为变）。
- 把 `typedef` 背后的真实类型换掉。

预留演进空间：

- 预计会加的参数可以先做成保留参数，或一开始就走数据驱动。
- 内部类型用不透明指针 / `typedef`，不要把 `float` 直接钉死在公共签名里（若将来可能改精度）。

**弃用路径：** 标记 deprecated → 警告（最好每个调用点只警告一次）→ 至少一个主版本后再删除。删除等于升主版本，并保留旧包可下载。

#### 9.4 API 审查（发版门禁）

两种互补机制：

- **预发布审查**：发版前集中看本周期所有公共接口 diff。
- **预提交审查**：改公共头文件必须先批准再合入。

目的只有一个：拦住「不经意破坏客户」的修改。源码能编过 ≠ 可以发给客户。

### 10. 文档与测试（第 9–10 章）

#### 10.1 文档是 API 的一部分

头文件只规定「怎么调用」，不规定「调用后发生什么」。没有行为说明的接口定义是不完整的。

至少要写清：

- 每个调用的行为、前置条件、错误与边界；
- 线程安全；
- 所有权（谁分配谁释放）；
- 复杂度/性能承诺（若客户会依赖）；
- 行为变更（发版说明）。

类型：Doxygen 一类从注释生成的参考手册、概述、示例/教程、Release Notes、许可证。  
对客户而言，**公共头文件上的注释比 `.cpp` 注释重要得多。**

建议：Doxygen 注释直接写在公共头文件；示例必须可编译、随版本测试。

#### 10.2 测试：保护客户的最重要措施

- 单元 / 集成 / 性能分层；API 产品通常还需要契约测试（「旧客户场景在新版本仍通过」）。
- 好测试：独立、可重复、失败时定位清晰、覆盖公共承诺而不是实现细节。
- **可测试性是设计属性**，不要等写完再测：
  - 依赖可注入，避免单例和隐藏全局；
  - 用桩/模拟隔离邻居；
  - 断言表达不变量；
  - 公共行为可测就不要测 private。
- 测试驱动（TDD）对公共 API 特别合适：先写「客户会怎么用」，再实现，接口会更小、更符合真实用例。
- 自动化进构建；看覆盖率，但覆盖率不是目标本身——**客户可见行为的回归**才是。

### 11. 脚本绑定与可扩展（第 11–12 章）

#### 11.1 脚本化

当 QA、工具链或产品需要 Python/Ruby/Lua 调 C++ 时再做。两种集成：

- **扩充**：C++ 做成脚本模块（`import`）。
- **嵌入**：应用程序内嵌解释器跑用户脚本。

技术路线（原书重点）：Boost.Python（控制细、手写包装）与 SWIG（多语言、接口文件生成）。无论哪种：

- 先有干净的 C/C++ API，再绑定；不要为脚本语言扭曲核心 API。
- 处理跨语言差异：所有权、异常、迭代器、继承/虚函数、重载。
- 绑定层本身也是 API，要版本化和测试。

#### 11.2 可扩展：对扩展开放，对修改封闭

三条路：

1. **插件（运行时）**：客户编自己的动态库，实现你定义的插件 ABI；宿主加载。适合算法族、第三方扩展。要有版本协商（min/max plugin API version），避免新宿主加载旧插件直接崩。
2. **继承（编译期）**：仅当基类**为继承而设计**（虚析构、稳定虚接口、文档化扩展点）。普通工具类不要打开继承。
3. **模板（编译期）**：策略类、CRTP。零开销，但扩展者必须会 C++ 模板，且往往要看到头文件实现。

选择：外部开发者、多语言、热插拔 → 插件；同进程 C++、静态多态 → 模板；面向对象定制 → 精心设计的基类。

### 12. 开发落地：日常工作流

把原书原则嵌进实际开发，而不是读完再忘。

#### 12.1 新增一个公共接口时

1. 写出 3～5 条真实用例（客户代码草稿），确认没有更小的表面能覆盖。
2. 问：这个符号明年还能删吗？不能删才放进公共头文件。
3. 选风格：C 边界 / C++ 类 / 模板 / 数据块。跨二进制边界默认 C 或 Pimpl。
4. 签名里写清：const、空值、所有权、错误。
5. 头文件自检：无 `using namespace`、无平台 `#ifdef`、无实现 `#define`、include 最小、单参数构造 `explicit`。
6. 同步写：Doxygen 行为说明 + 至少一个可编译示例 + 回归测试。
7. 走 API 审查再合入。

#### 12.2 修改已发布接口时

```text
只加不改 → 次版本
改行为 / 改布局 / 删符号 / 加纯虚 → 主版本
修 bug 且行为对外不可察 → 补丁
```

弃用必须给迁移路径和至少一个完整发版周期的警告期。

#### 12.3 代码评审看什么（可直接当 PR 模板）

**必须拦下：**

- [ ] 公共头文件出现实现细节、私有类型完整定义、或平台分支
- [ ] 无必要的新公共符号或新虚函数
- [ ] 单参数构造未 `explicit`
- [ ] 只读参数按值传大对象
- [ ] 公共头文件 `using namespace`
- [ ] 所有权/错误/线程安全未写进注释
- [ ] 改了已发布类的布局或虚表却未升主版本
- [ ] 给客户必须实现的基类新增纯虚函数
- [ ] 无测试、无示例

**应当讨论：**

- [ ] 是否该 Pimpl
- [ ] 是否该工厂而不是公开构造
- [ ] 便捷方法和核心方法是否该分层
- [ ] 默认参数是否把实现常量钉死在 ABI 上
- [ ] 单例能否换成上下文对象

#### 12.4 头文件骨架（推荐形态）

```cpp
#ifndef MYPROJ_WIDGET_H
#define MYPROJ_WIDGET_H

#include <memory>
#include <string>

namespace myproj {

/// Widget 负责……（一句话）。线程安全：……。错误：……。
class Widget {
public:
    explicit Widget(const std::string& name);
    Widget(const Widget&);
    Widget& operator=(const Widget&);
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;
    ~Widget();

    /// 不修改状态。失败时……
    bool IsValid() const;

    /// 输出写入 *out；out == nullptr 表示忽略该项。
    void GetBounds(int* width, int* height) const;

private:
    class Impl;
    std::unique_ptr<Impl> mImpl;
};

}  // namespace myproj

#endif
```

实现、平台头、默认魔法数全部留在 `.cpp`。

#### 12.5 按项目类型裁剪

**给其他 C++ 模块用的库（同仓库）：**  
最小完备 + const + 命名空间 + 测试。Pimpl 可选（编译时间痛再上）。

**跨 DLL/so、多语言、长期发版：**  
Pimpl 或纯 C ABI、符号导出、语义化版本、ABI 审查、C 头文件为稳定边界。

**嵌入式 / 固件对外协议：**  
把寄存器布局、二进制包、命令字当成 API：版本字段、向后兼容、不要随意改枚举值；实现可换，协议要稳。便捷命令集与核心协议分层。

**工具脚本 / QA：**  
核心保持 C++，外加一层绑定；不要让 Python 形状反噬核心模型。

### 14. 可当墙贴的十条

1. 公共符号是承诺，不确定就不要发布。  
2. 头文件是产品，`.cpp` 才是实现。  
3. 隐藏细节：Pimpl、前向声明、禁止头文件平台宏。  
4. 核心小、便捷另包。  
5. const、explicit、命名空间，没有例外。  
6. 签名写清所有权和错误。  
7. 不要用性能当借口破坏抽象；用数据证明瓶颈。  
8. 发版后只演进不改契约；破坏兼容就升主版本。  
9. 没有行为文档和自动化测试的接口，等于没做完。  
10. 单例、友元、公共 `#define`、抽象基类乱加纯虚，默认拒绝。

## 【完整拓展详情】

## 1.1 怎么读这份文档

有编程基础的人，最容易把这本书读成「一堆 C++ 技巧」。那会错过主线。

**主线只有一句：** 每一个已经发布的公共符号，都是你对其他工程师的长期承诺。实现可以换，承诺很难收回。全书的模式、`const`、Pimpl、版本号、测试，都是在降低「守住承诺」的成本。

建议读法：

1. 先读第 1 章（心智模型），大约十分钟。读完应能回答：API 和「一堆函数」差在哪。
2. 第 2–3 章是全书重心：优质接口长什么样，以及设计过程在想什么。每节开头有**一句话**，可先扫标题再按需深入。
3. 第 4–6 章把原则落到 C++：风格、头文件纪律、模式。看到某个语言细节时，回头对照它服务的是哪条原则。
4. 第 7–8 章是发版之后：兼容性、文档、测试、扩展。
5. 第 9 章用一个小接口把前面串起来。读完应能自己走一遍设计。

书中的「用户 / 客户」= 调用你接口的程序员或程序，不是产品最终用户。

## 1.2 先建立心智模型

### 1.1 一句话

写给别人（或三个月后的自己）调用的头文件、ABI、协议、脚本绑定，都是 API。好 API 的首要目标不是「功能多」，而是：**在提供所需功能的前提下，新版本对客户代码的影响最小，理想是零影响。**

### 1.2 为什么实现可以改、接口很难改

日常写应用时，改一个内部函数往往只影响本模块。API 不同：客户已经按你的头文件写了代码、编了二进制、写了测试、做了脚本绑定。你改一个签名，他们要改代码、重编、重测、再发版。成本在客户那边，而且客户可能有成千上万。

所以会出现这种不对称：

| | 改实现 | 改已发布接口 |
|--|--------|--------------|
| 客户代码 | 通常不用动 | 几乎都要动 |
| 客户二进制 | 有时要重链，Pimpl 后常常不用 | 布局/虚表一变就必须重编 |
| 你自己的自由度 | 高 | 极低 |

书里把这种关系比作建筑承包：客户（调用方）依赖你按图纸施工。图纸（接口）一改，整栋楼的依赖都要返工；墙里的钢筋怎么绑（实现）客户并不关心，只要承重承诺还在。

### 1.3 C++ 把这件事变得更难

很多语言的「接口」主要是源码契约。C++ 还有一层：**头文件会把对象布局、内联代码、模板实现泄漏给客户编译器**。客户 `#include` 你的 `.h` 时，不只是在「调用」，还在按你今天的内存布局生成代码。于是：

- 你在私有段加一个 `int`，对象大小变了 → 客户旧 `.o` 和新库对不齐 → **二进制不兼容**。
- 你把一段实现写进头文件当 `inline`，以后改这段逻辑，客户必须全部重编。
- 模板隐式实例化时，算法源码直接出现在客户的编译单元里。

这就是为什么这本书反复强调 Pimpl、前向声明、不要把实现写进公共头文件：不是洁癖，是 C++ 的编译模型决定的。

### 1.4 API 描述的是工程师之间的软件

书中有一句应记住的话（大意）：API 描述的是其他工程师用来构建他们软件的软件。因此它必须有良好的设计、文档、回归测试，并且保证发布之间的稳定性。

这意味着 API 工作比「把功能写出来」多四件事：

1. **审查**：初级工程师不完全理解兼容性时，很容易「修个 bug」却改变客户依赖的行为。发版前要有人专门看公共接口 diff。
2. **长寿命**：前期设计成本看起来高，换来的是以后能改实现、能优化、能换平台，而不赶客户升级。
3. **文档**：客户常常没有实现源码。头文件告诉编译器类型，文档告诉人行为。
4. **自动化测试**：你改实现时，必须有一套用例证明「客户需要的行为还在」。

### 1.5 为什么要做 API，以及何时不必做

做 API 的收益（对「给别人用的模块」几乎总是成立）：

- **隐藏实现**：将来换算法、换分配器、换平台，客户无感。否则客户会把你的内部细节编进他们的代码，你就被锁死。
- **延长寿命**：系统各部分若互相掏内部，会变成「大泥球」——脆弱、僵硬、难复用、只有原作者敢改。
- **模块化 / 去重**：同一逻辑只维护一处。很多 API 的诞生方式就是：先发现重复，再抽成统一入口。
- **消灭硬编码**：`GetLogFilename()` 替换散落的 `"myprogram.log"`。
- **可优化**：所有读写都走同一入口时，你才知道何时缓存失效。客户各自访问内部数据时，你无法安全加缓存。

但也有「不要为 API 而 API」的时候：

- 模块明确只在本程序内部、没有第二客户，为「稳定公有接口」付的设计税可能不值。这**不是**写烂代码的理由，只是不必把每个 `.h` 都当成对外产品。
- 选用第三方 API 时要看：许可证会不会绑死产品、功能是否真匹配（例如 1D FFT 库做不了你要的 2D）、有没有源码/文档。缺这几样，集成成本会反向转移到你身上。

**开发判断：** 只要这个头文件可能被另一个团队、另一个进程、下一任维护者当成契约，就按 API 来设计。

## 1.3 优质 API 的六项特征

第 2 章是全书最重要的一章。后面所有技巧都可以还原成：它在强化这六条里的哪几条。

写任何公共符号前，用这六条自检：

1. 问题域建模要对  
2. 实现细节要藏住  
3. 最小，但完备  
4. 易用（可发现、不易误用、一致）  
5. 正交，资源安全  
6. 松耦合、高内聚，并且稳定、有文档、可测  

### 2.1 问题域建模：给逻辑，不给实现

**一句话：** 客户应该看到领域对象和操作，而不是文件格式、套接字、压缩算法、平台 `#ifdef`。

错误抽象的典型样子：一个叫 `FileDownloader` 的类，公共接口里却是 `SocketConnect`、`GetFd`、`WriteBuffer`。客户本想「把这个 URL 存到磁盘」，你却逼他们扮演 TCP 程序员。后果有三：

- 学起来难（心智模型是实现，不是任务）；
- 换实现不可能（HTTP/2、线程池、内存映射一上，旧方法名全部撒谎）；
- 误用容易（客户拿到底层 fd 之后，你无法再保证不变量）。

书里强调：类应该定义**做什么**，而不是**如何做**。模型也不必一次做完美——需求变了要重新评估对象模型——但不要「比需求更通用」。工程师常被「将来可能用到」诱惑，给 API 加抽象层。三个理由拒绝它：

1. 你预想的通用性可能永远用不到；
2. 真用到时，你已经更懂问题，方案往往和当初设想不同；
3. 真要加功能时，简单 API 比复杂 API 更好加。

**自检：** 把头文件给非该模块作者看，他能否讲清「这套接口在干什么」。讲不清，通常是模型错了，不是文档少了。

### 2.2 隐藏实现：物理隐藏 + 逻辑隐藏

**一句话：** 客户拿不到、也访问不了实现；你才能在不惊动他们的情况下换掉实现。

两层含义：

| 层次 | 做法 | 失败时 |
|------|------|--------|
| 物理隐藏 | 声明在 `.h`，定义在 `.cpp`；客户没有实现源码也要能用 | 把头文件写成「带实现的脚本」，客户被内联代码钉死 |
| 逻辑隐藏 | `private` / 不完整类型 / 不把内部类放进公共头 | 成员是 `public`，或 `protected` 变成客户的挂钩 |

`public` / `protected` / `private` 不是装饰。`protected` 尤其危险：你以为只给「自己人」的子类用，客户却会继承并依赖这些挂钩。将来你改内部，等于改他们的代码。书里提醒：用户会利用一切你露出来的钩子——不是因为他们恶意，而是因为那是「能用的路」。一旦这条路存在，你就失去了改内部的自由。

数据成员应始终是私有的。唯一看起来合理的反例是「为了快，避免函数调用」。即便热路径上，内联的 getter 通常已经把开销打掉；暴露字段换来的是：再也无法加校验、改表示、做惰性计算、保持不变量。

还要藏三样东西：

1. **不必公开的方法**。只被本类其他公共方法用的逻辑，做成 `.cpp` 里的静态函数，或放进 Pimpl。写在 `private:` 里仍然会出现在头文件里，客户能看到「你内部有这些步骤」。
2. **纯实现类**。烟花特效里的 `Particle`、下载器里的 `SocketState`，客户永远不该知道它们的名字。
3. **平台差异**。公共头文件里的 `#ifdef TARGET_IOS` 会让不同平台变成不同 API，并逼客户写同样的 `#ifdef`。正确做法是同一套方法 + `HasGPS()` 这类查询，`#ifdef` 只留在 `.cpp`。

Pimpl 把上述几条一次做完：公共类只留一个指向不完整类型的指针，布局和私有方法全部离开头文件。第 5 章会展开。

### 2.3 最小完备：每个公共符号都是生命周期承诺

**一句话：** 客户需要的都要有；不确定要不要的，就不要提供。加上容易，删掉会逼客户改代码。

完备来自需求/用例，不是来自「我觉得可能用得上」。最小来自奥卡姆剃刀：**若无必要，勿增实体。**

虚函数也是承诺。每加一个 `virtual`，就多锁定一份继承契约：

- 基类一个「无害」改动，可能弄坏客户子类（脆弱基类）；
- 客户会用你预想不到的方式重写（例如在线程安全 API 里忘了加锁）；
- 默认实现若维护了内部不变量，客户重写时漏掉那些调用，对象会处于不一致状态；
- 还有虚表查找和对象体积（通常次要，但小对象海量实例时要知道）。

「便捷 API」不要污染核心。书中用 OpenGL / GLU / GLUT 分层：核心保持小而稳，便利功能做成独立层。这叫**渐进公开**（progressive disclosure）——先让简单任务更简单，复杂能力放在第二层，专家才需要看见。

**开发判断：** 评审公共 PR 时问「去掉这个符号，有没有客户完不成他的用例？」没有，就先不要合入。

### 2.4 易用：最小惊奇

**一句话：** 简单任务应该从函数签名就能看懂；整库的命名、参数顺序、错误策略必须一致；能让编译器挡住的误用，就不要留到运行时。

拆成三个可操作的子问题。

**可发现性。** 用户应能通过 API 自身明白怎么用，而不是先读一篇教程。最有效的手段是：直观的对象模型 + 完整、好记、无歧义的名字。`GetCurrentValue` / `GetCurrValue` / `GetCurValue` / `GetCurVal` 四种同时存在，就是在逼客户背单词表。缩略语是可发现性的敌人。

**不易误用。** Scott Meyers 把「难用错」当成通用接口准则。最常见的误用是：多个同类型参数，客户记错顺序。

```cpp
// 能编译，语义却可能全反：两个 bool 在类型系统里是同一个东西
std::string FindText(const std::string& text,
                     bool search_forward,
                     bool case_sensitive);

// 编译器成为盟友：调换两个枚举会直接无法编译，调用处也自描述
enum class Direction { Forward, Backward };
enum class Case { Sensitive, Insensitive };
std::string FindText(const std::string& text,
                     Direction direction,
                     Case sensitivity);
```

同理，`Date(int, int, int)` 分不清年月日；改成 `Date(Year, Month, Day)` 这类轻量包装类型，顺序错误会变成编译错误。原则：**避免编写拥有多个相同类型参数的函数。**

工厂返回 `unique_ptr` 而不是裸指针，也是「不易误用」：所有权写在类型里，客户不太会漏删或双重删除。

**一致性。** 同一概念用同一词语。已经用了 `Begin`/`End`，就不要夹杂 `Start`/`Finish`。互补操作要用成对术语：`Add/Remove`、`Open/Close`、`Lock/Unlock`，不要 `OpenWindow` 配 `DismissWindow`。参数顺序全库一致。C 标准库里 `memcpy` 和 `strncpy` 的源/目的顺序相反，是反面教材——手册里有线索，人还是会抄反，然后内存出错。

一致性的另一面是**沿用客户已经会的习惯**。容器和迭代器尽量像 STL，因为 C++ 程序员已经为那套模型付过学习成本。像汽车：换一辆车不该重新学刹车在哪。

**平台独立**也属于易用：客户代码不应因为换平台就换一套调用方式。见 2.2 的 `HasGPS()` 例子。

### 2.5 正交：改一个属性，别顺带改另一个

**一句话：** 正交的 API 意味着函数没有副作用；同一信息只有一个权威来源；概念不重叠。

数学上，正交向量互不影响。API 上：设置温度的方法只该改变温度，不该悄悄改变水压。书里用「廉价汽车旅馆的淋浴旋钮」作比喻——一个旋钮同时搅动两个属性，人无法预测行为。

两个操作要点：

1. **少冗余。** 同一事实不要在两个公共接口里用两种方式表示，否则它们会不一致。
2. **增独立。** 算法和容器分离（STL 的路）就是正交：一套算法可以套多种容器，改容器不影响算法接口。

正交直接降低测试成本：行为的影响范围是局部的、有边界的。非正交接口的 bug 会从「改了 A」跳到「B 莫名坏了」。

资源安全是 C++ 特有的正交邻居：没有 GC，接口必须把所有权讲清楚。优先 RAII 和智能指针；`new`/`delete` 混用、数组 `delete` 错误、空指针、二次释放，都是接口把所有权说糊之后的症状，而不只是实现马虎。

### 2.6 松耦合、高内聚

**一句话：** 耦合是组件之间互相依赖的强度；内聚是组件内部是否围着同一职责。目标是：改 A 时，B 尽量不用改。

书里区分两种耦合，评审时不要混：

- **API 内耦合**：你库里类与类之间。
- **API 与客户的耦合**：你的设计如何影响客户程序的内聚。API 越大、参数越多，客户越容易变成「调用集散地」。最小完备本身就会降低这种耦合。

降耦合的常用手法（从便宜到贵）：

1. **只通过名字耦合。** 若 A 只需要 B 的指针/引用，不要 `#include "B.h"`，写 `class B;` 即可。这是编译隔离的第一刀。
2. **能做成非成员非友元函数，就不要做成成员。** 成员函数看见类的全部私有状态，耦合更紧；只通过公共 getter 工作的自由函数，和类的实现是解耦的。
3. **需要时用数据冗余换耦合。** 若日志类只为了取用户名而持有整个 `User` 对象，把用户名以 `string` 传进去，两个类就解开了。冗余的代价是：用户改名后旧日志不会自动更新——这是产品决策，不是语法决策。有时冗余是对的。
4. **管理器类。** 一堆低层设备类不要让每个业务对象都去依赖；引入 `InputManager`，业务只依赖管理器。加新设备或新业务对象时，边数按加法长，不按乘法长。
5. **回调 / 观察者 / 通知。** 不要让 `NameCache` 直接调用 `Lobby::SetPlayerName` 再调用 `InGame::SetPlayerName`。让感兴趣的对象注册监听。代价是必须处理：**重入**（回调里又调用你）、**生命周期**（监听者销毁后必须能注销）、**重复注册**。

内聚的反面是「一个类又下载、又解析、又画 UI」。名字说不清职责时，通常已经低内聚。

### 2.7 稳定、有文档、可测试

稳定 ≠ 永不改变。稳定是：

- 接口有版本；
- 升级默认向后兼容；
- 设计留有扩展点（演进，而不是推倒）；
- 行为写在文档里（头文件不够）；
- 自动化测试锁住客户依赖的行为。

这三条把第 2 章接到第 8–10 章。没有它们，前五条做再漂亮，一次「顺手改默认值」就会把客户打穿。

## 1.4 从需求到签名：设计过程在想什么

### 3.1 一句话

敏捷的用户故事不会自动长出好 API。分析 → 设计 → 实现是循环，不是瀑布；其中设计必须显式存在。先对象层次（整体由哪些部分组成），再类层次（is-a），再函数签名。

### 3.2 技术债为什么对 API 更致命

应用内部的脏代码，团队咬牙可以重写。API 一旦被客户依赖，脏接口会变成**客户依赖的特性**。书中用技术债解释衰退：第一次交付就像借钱，少量债务能加速，但若不偿还，利息会拖住整个组织。

McConnell 区分两种债：无意的（初级错误、并购来的烂代码）和有意的（先赶工期再还）。无论哪种，API 上的警告信号是：

- **脆弱**：一处改动引发无关处出问题，因为内部细节被跨模块依赖。
- **僵硬**：简单改动都要大重构。
- **顽固**：代码和周边缠死，或绑着领域特例，无法复用。
- **不可转移**：只有原作者敢动。大规模代码库里这等于存在无人区。

依赖关系无节制增长、无关模块互相掏内部，就是「大泥球」。还债的时机往往是：维护旧代码的时间已经超过给客户加特性的时间。对 API 而言，预防比偿还便宜得多——因为偿还常常等于发一个不兼容的主版本。

### 3.3 架构：先画部分关系，并写下「为什么」

架构阶段识别主要抽象、创造关键对象、选择风格。文档要写两件事：**高层结构**，以及**原理**（为什么选这个、放弃了什么）。后人若只看到结构、看不到取舍，会把接口学成一堆偶然的名字。

发版前的设计审查应有三种角色：架构师、实现者、客户。缺客户时，你审的是「我们自己觉得好用」，不是「调用方觉得好用」。

### 3.4 类：一个类一件事；继承是最后才用的耦合

创建类等于创造一种新类型，要像语言设计者一样问：

- 继承还是组合？公有继承还是私有？要不要多继承？
- 要不要抽象接口（纯虚）？
- 创建/销毁是客户 `new`/`delete`，还是工厂？要不要智能指针？
- 有资源就必须处理拷贝/移动（或禁止拷贝）。
- 是一个类型还是一族类型（模板）？
- `const` / `explicit` / 运算符 / 转换 / friend？
- 性能与内存是否反过来约束接口？

**组合优于继承。** 继承让子类和基类的公有、保护成员全部耦合；组合可以只持有指针，头文件里甚至只要前向声明。经典反例是「圆继承椭圆」：数学上圆是椭圆的特例，但椭圆能独立改长轴短轴，圆不能——子类无法在行为上替换基类。这就是下一节的 LSP。公开继承只留给真正的 is-a 且行为可替换；否则用组合，或抽一层双方都遵守的 `Shape`。

不打算被继承的类：析构函数不要无故变虚，避免客户把它当基类用。要被继承的类：虚析构，并且虚函数集是你明确愿意承诺的契约。

多继承：除了纯接口和 mixin，尽量不用。

### 3.5 三条设计原则，用 API 的语言重新说

**Liskov 替换（LSP）。** 若 S 是 T 的子类，则任何 T 的客户都应能在不知情时换成 S，行为承诺仍然成立。`is-a` 是分类学；LSP 是客户假设。圆/椭圆、正方形/矩形之所以著名，是因为「数学子集」不等于「可替换行为」。API 里违反 LSP 的常见样子：子类重写后缩小前置条件的反面（基类允许的调用，子类抛异常）、或悄悄忽略基类文档里的保证。

**开放-封闭（OCP）。** 对扩展开放，对修改封闭。类一旦发布，唯一该改的是 bug；新能力通过新类型、组合、插件完成，而不是给已发布类加职责。简单工厂做不到对修改封闭——每加一种产品都要改工厂内部。可注册的工厂、插件、策略对象，才是 OCP 在 API 上的样子。

**迪米特法则。** 只与直接朋友说话。`a.GetB()->GetC()->Do()` 意味着客户依赖了 B 和 C 的结构；B 的内部一改，客户全断。应让 A 提供客户真正要的操作，而不是把内脏递出去。

### 3.6 函数：每次加一个公共函数，都在做一串选择

自由函数要想：静态与否、值/引用/指针、const、默认参数、返回方式、运算符、异常规格。成员函数再加：虚/非虚、纯虚与否、访问级别、`explicit`。

这些选择会改变 API 质量，例如：

- 不修改对象的成员标 `const`，客户才能在 `const` 对象上调用，这也是文档。
- `const T&` 传参减少拷贝（性能章）。
- 内联有时更快，但把实现钉进头文件，伤害二进制兼容（版本章）。

命名规则（可当规范）：

- 读写用完整前缀：`GetZoomFactor` / `SetZoomFactor`，不要四种缩写并存。
- 是非问题用 `Is`/`Has`/`Are`：`IsEnabled`。STL 的 `empty()` 更短，但也更含糊（是「空吗」还是「清空」？）。对外 API 更宜选不易误用的那一种。
- 动作动词要强：`Save`、`Enable`。自由函数把对象名编进动词：`OpenFile`。
- 用正面概念：`IsConnected` 而不是 `IsUnconnected`，避免 `!IsUnconnected` 双重否定。
- 名字应覆盖函数真正做的全部事情。`SharpenAndSaveImage` 若太长，说明函数职责太多，该拆。
- 不要以下划线开头（留给实现和标准）。
- 成对操作用成对术语。

参数：名字要自描述（`haystack`/`needle` 优于 `s1`/`s2`）；类型要约束（钱不要用 `float`）；个数尽量短，经验上超过 5 个就该考虑打包成结构体或拆函数。

错误处理全库只能有一种主策略（返回码、异常、或 `std::expected` 一类），并写进文档。同一层混用三种，客户无法形成肌肉记忆。

## 1.5 四种风格：同一功能，四种契约

### 4.1 一句话

风格不是口味，是在「封装 / ABI 稳定 / 扩展方式 / 学习成本」之间做取舍。可以、而且经常应该，在不同边界用不同风格。

### 4.2 对照

| 风格 | 客户看见什么 | 真正强在哪 | 真正弱在哪 |
|------|--------------|------------|------------|
| 纯 C | 自由函数 + 结构体 + 句柄 | ABI 稳、跨语言、嵌入式、插件边界简单 | 无语言级封装；名字靠前缀；所有权靠约定和文档 |
| C++ 对象 | 类、封装、继承、虚函数 | 领域模型清晰；同一进程的 C++ 客户最好用 | 布局和虚表一变就破 ABI；需要 Pimpl 才能跨库稳 |
| 模板 | 类型参数化的接口 | 零开销抽象、静态多态、策略 | 编译慢；错误难读；隐式实例化会把实现送进客户编译单元 |
| 数据驱动 | 打包好的命令/属性丢给处理程序 | 加字段不一定改函数签名；脚本和 RPC 友好；偏向前兼容 | 类型弱；调试难；不适合热路径上的细粒度调用 |

书中用同一音频库的多种绑定说明：客户体验可以完全不同，底层可以是同一份实现。这正是「包装器」模式的价值。

### 4.3 实践中怎么组合

常见、也最符合本书精神的组合：

- **稳定边界**（`.dll` / `.so` / 插件 / 给其他语言）：纯 C，或 C++ 类 + Pimpl。
- **库内部**：正常 C++ 对象模型。
- **要客户扩展算法、且能接受重编**：模板策略。
- **要加配置项却不想改函数签名**：数据驱动（属性包、命令结构、键值）。可变参数列表天生更「向前兼容」，因为旧客户可以忽略新字段。

不要在一个公共头文件里同时展示四种风格。客户的学习模型必须单一；风格切换发生在边界上，而不是每一行调用上。

## 1.6 C++ 用法：语言特性都在为哪条原则服务

第 6 章看起来像编码规范，实质是第 2 章的实现清单。下面按「原则 → 语言机制」来记，而不是按语法条目背。

### 5.1 命名空间：防止碰撞，也防止你污染客户

公共符号必须有 namespace 或统一前缀。在公共头文件的全局作用域写 `using namespace xxx;` 等于拆掉命名空间：客户包含你的头，他们的全局就被你的名字占领。客户头文件里写 `std::string` 全名。内部符号可放 `detail`，并在文档里写「不要依赖」。

这是**最小完备 + 一致性 + 不误用**在符号层面的体现。

### 5.2 构造、拷贝、explicit：管住对象的诞生和复制

编译器可能生成默认构造、析构、拷贝、赋值（以及移动）。类若拥有资源，必须显式定义或删除这一组（三大件 / 五法则 / 零法则）。只写析构、让编译器生成浅拷贝，是双重释放的经典来源。

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t n);
    Buffer(const Buffer&);
    Buffer& operator=(const Buffer&);
    ~Buffer();
    // 或：定义了其中之一，其余要么定义要么 = delete
};
```

不想被拷贝就写出来：

```cpp
Buffer(const Buffer&) = delete;
Buffer& operator=(const Buffer&) = delete;
```

**单参数构造函数加 `explicit`。** 否则 `Buffer` 会从 `size_t` 隐式转换，函数重载解析会把一个整数悄悄变成对象，类型系统被打穿。这是「不易误用」。

### 5.3 const 贯穿公共 API

不修改 `*this` 的成员标 `const`。不修改的参数用 `const T&` / `const T*`。这既是编译器能查的文档，也让 `const` 对象可调用。

返回值要小心：书中建议**优先按值返回**，而不是返回内部成员的 `const` 引用。按值更安全（没有悬空、客户也不必担心对象销毁后引用还在）。返回 `const std::string&` 看起来高效，但执着的客户可以 `const_cast` 掉常量性，直接改你的私有数据——逻辑隐藏被语言后门拆掉。关注性能时再考虑引用返回，并接受这条风险。

### 5.4 模板：隐式实例化是在暴露实现

对外提供类模板时要想三件事：隔离、效率、跨平台。关键分叉：

| | 隐式实例化 | 显式实例化 |
|--|------------|------------|
| 做法 | 定义放头文件，客户任意类型都能用 | 定义放 `.cpp`，你只对列出的类型实例化 |
| 换来的 | 灵活 | 实现隐藏、编译更快、二进制更可控 |
| 代价 | 暴露算法、拖慢客户编译、跨 `.so` 易碎 | 客户不能随意用新类型 |

ABI 稳定的跨库边界，不要把重模板接口直接做成导出符号。可以内部用模板，边界上用具体类型或纯 C。

### 5.5 运算符：只重载「看起来像内建」的含义

`+` 不要发射导弹。对称运算（`==`、`+`）优先非成员，以便隐式转换在两侧都工作；修改自身的（`+=`、`[]`）做成员。团队里 C 背景客户多时，命名函数往往比运算符更不易误用。

### 5.6 参数传递：把意图写进类型

| 意图 | 推荐 | 原则 |
|------|------|------|
| 只读、非空对象 | `const T&` | 正交（不拷贝）、性能 |
| 只读、可空 | `const T*` | 空指针是合法信号 |
| 输出 / 可选输出 | 指针（空表示不要这份输出），或返回值 | 不易误用 |
| 转移所有权 | `T` 按值（可移动）或 `unique_ptr<T>` | 所有权在签名里 |
| 共享所有权 | `shared_ptr<T>` | 明确共享，不要随手上 |
| 内建小类型 | 按值 | `const int&` 无收益 |

默认参数：若默认值是实现里的魔法数字，**用重载代替默认参数**，把默认值藏进 `.cpp`。签名上的默认值是接口的一部分，改它会在「源码仍能编过」的情况下改变行为。`nullptr` / `""` 这类哨兵可以留在签名上，因为它们本身就是契约。

### 5.7 宏、friend、导出

`#define` 无作用域、无类型、会泄漏实现。公共常量用 `const` / `constexpr` / `enum class`。宏只留在 `.cpp` 或内部头。

`friend` 破坏封装，把两个类的内部绑死。测试和「图方便」都不是给客户 API 开后门的理由。测公共行为；非要测内部，用测试构建或内部夹具，不要把 `friend` 写进发布头文件。

DLL/so 要有明确导出宏，不要默认导出一切——导出表面就是 ABI 表面。全库统一命名风格（书中示例：成员 `m`、静态 `s`）。每个头文件：include guard（或 `#pragma once`）、自己的依赖声明齐全、一个命名空间。头文件应能被一个空 `.cpp` 单独编译——这是「自给自足」的测试。

## 1.7 模式：只抓对 C++ API 真正关键的几个

原书不讲完 GoF。它只选会改变封装、创建方式和耦合的模式。

### 6.1 Pimpl：默认习惯，而不是高级技巧

把私有数据和方法挪到 `.cpp` 的 `Impl`，公共类只留指针：

```cpp
// recorder.h —— 客户看见的只有契约
#pragma once
#include <memory>
#include <string>

namespace acme {

class Recorder {
public:
    Recorder();
    Recorder(const Recorder&);
    Recorder& operator=(const Recorder&);
    ~Recorder();

    void SetPath(const std::string& path);
    bool Start();
    void Stop();

private:
    class Impl;
    std::unique_ptr<Impl> impl_;
};

}  // namespace acme
```

```cpp
// recorder.cpp —— 布局、依赖、私有方法都在这里
#include "recorder.h"
#include <fstream>
#include <vector>

class acme::Recorder::Impl {
public:
    std::string path;
    std::ofstream out;
    std::vector<char> buffer;
    bool Start();
    void Stop();
};

// 构造 / 拷贝：决定深拷贝还是禁止拷贝。浅拷贝 unique_ptr 会编译失败，这是好事。
```

收益对应第 2 章几乎每一条：

- 头文件即真正的公共接口（最小、可发现）；
- 客户即使用宏把 `private` 改成 `public` 也拿不到 `Impl` 的定义（逻辑隐藏）；
- 公共头不再包含实现依赖（降耦合、加快客户编译）；
- 对象公共布局只是一个指针，加字段通常不破 ABI。

代价：一次堆分配和一次间接。热路径上的极小值对象可以不用。一旦类会跨库发版，优先 Pimpl。

拷贝语义必须显式决定：深拷贝就自己写；不可拷贝就 `= delete`。不要让两个对象指向同一块 `Impl` 然后双重释放。

不想上 Pimpl 的最低限度：把仅访问公有成员的私有方法改成 `.cpp` 里的静态函数，至少不要在头文件里展览内部步骤。

### 6.2 工厂：当构造函数说不了你要说的话

构造函数有语言强加的限制：

- 创建时必须写出编译期已知的具体类型（静态绑定）；
- 不能是虚函数（对象还没构造完，虚调用没有完整动态类型）；
- 失败只能抛异常或造出「僵尸对象」，不能返回空或错误码；
- 名字被钉死成类名，无法表达 `CreateFromFile` / `CreateFromBuffer` 的差别。

工厂只是普通函数调用，可以返回基类指针、可以失败、可以按字符串或注册表选择类型。抽象基类（一个或多个纯虚函数的类）描述「所有产品必须遵守的契约」；工厂返回这个契约，而不是具体类。

```cpp
class IRenderer {
public:
    virtual ~IRenderer() = 0;
    virtual void Render() = 0;
};

std::unique_ptr<IRenderer> CreateRenderer(const std::string& name);
```

析构必须是虚的：客户通过基类指针删除时，才会调用到派生析构。

扩展方式有两档：

- **简单工厂：** 内部 `if/else` 或 `switch`。加新产品要改工厂——违背 OCP，但小 API 够用。
- **可注册工厂：** 产品提供 `Create`，启动时 `Register("gl", &GlRenderer::Create)`。主程序不必知道具体类，插件可以在运行时加入。注意：不必把内置实现的类名暴露给客户。

所有权：返回 `unique_ptr<IRenderer>`，不要返回裸指针。这是「不易误用」直接写进类型系统。

### 6.3 包装：代理 / 适配器 / 外观

三者按「和原接口差多远」排列：

- **代理：** 一对一转发，可加权限、延迟、日志。
- **适配器：** 把已有接口转换成客户期望的形状。
- **外观：** 把一堆子系统收成一条简单主路径。

写新 API 时极常见的一步是：先不要改旧实现，在外面加一层干净外观。遗留库、给 C 客户包 C++、不想把第三方依赖泄漏给客户，都属于这一类。代价是多一层调用和可能的额外状态；收益是你拥有了可以演进的新契约。

### 6.4 观察者：解开「谁变化」和「谁在意」

当 A 不该知道 B、C、D 的名字，但又要在事件发生时通知它们，用注册监听，而不是 A 直接调用 B、C、D。实现时盯住：

- **推 vs 拉：** 通知里带全部数据，或只说「变了」让观察者来取。
- **重入：** 回调里可能再次进入你的 API，包括再次订阅/取消。至少保持状态一致；更好是允许重入。
- **生命周期：** 必须能干净注销。监听者销毁后还发通知会崩溃。
- **重复注册：** 默认应拒绝或去重，避免一次事件调两次客户代码。

### 6.5 单例：默认不选

单例是更体面的全局变量。它带来全局状态、隐藏依赖、破坏可测性（测试无法换成假对象），并且一旦客户按「全世界只有一个」来写，你就很难变成「每会话一个」。

替代：

- 依赖注入：需要它的对象在构造时传入；
- 会话/上下文对象：生命周期跟业务走，而不是跟进程走；
- 「工具箱单例」只包真正全局的东西（例如系统剪贴板）。领域对象不要做成单例。

问自己：将来会不会需要两个实例？只要「可能」，现在就不要做成单例。

## 1.8 性能：接口属性，不是事后补丁

### 7.1 一句话

实现可以以后优化，接口很难事后优化。但也不要为速度扭曲问题域抽象。先正确，再量测，再优化实现。

Amdahl 定律：只优化占 1% 时间的路径，整体几乎不变。用真实负载剖析，不要凭感觉把 getter 改成公共字段。

关注五类性能，它们在 API 上的表现不同：调用耗时、内存、库体积、启动/加载、**客户编译时间**。最后一项常被忽略，却是 C++ 库最容易伤害客户的地方。

### 7.2 调用层：拷贝、切割、所有权

只读对象用 `const T&`，避免拷贝整棵对象树。按值传多态对象还会**切割**：形参按基类大小构造，派生部分被切掉。`const Base&` 不会。

工厂和缓冲区的所有权一旦在第一版写错（返回必须拷贝的大对象、强迫客户自己 `new`），以后改签名就是兼容性事件。第一版就把所有权和拷贝语义设计对，通常不伤害领域模型。

### 7.3 编译层：`#include` 就是耦合

编译时间大体随头文件数量和深度增长。

- **不要提供「无所不包」的总头作为唯一入口。** `windows.h` 那种体量会让只用一角的客户也吞下整库。可以另提供分模块的小头；总头若存在，应是便利层，不是唯一层。
- **能前向声明就不要 include。** 条件：只用指针/引用、不调用成员、不当作值成员或基类（后两种需要完整类型以知道大小）。只前置声明你自己 API 里的符号，不要给客户前置第三方类型充数。
- **头文件必须声明自己的全部依赖**（include 或前置），否则客户会依赖「碰巧的包含顺序」。健壮性在这里优先于「再少一条 include」。
- Pimpl 把实现依赖推进 `.cpp`，是编译隔离最强的一招。
- 冗余 include guard（包含前先 `#ifndef`）对极深包含图有历史数据支持，现代编译器收益变小；正确的普通 guard / `#pragma once` 仍是必须。

**不要为了「可能快一点」把大量函数塞进头文件当 inline。** 它拖垮客户编译，并把实现钉死。先提供正确抽象；需要时再对剖析过的热点做 inline 或局部快路径（例如迭代器、连续存储），而不是第一天就让客户走「直接掏数组」的捷径。

初始化列表优于先默认构造再赋值。常量用真正的常量，让编译器参与。这些都不扭曲抽象。

## 1.9 版本：发布之后只能演进，不能改契约

### 8.1 一句话

**Evolve, don't change.** 已经发布的行为是客户代码的一部分。你可以加；你不能悄悄换含义。

### 8.2 版本号在说什么

典型 `主.次.补丁`：

| 位 | 何时加 | 客户旧代码 |
|----|--------|------------|
| 主 | 不兼容：删接口、改行为、破 ABI | 必须改代码或钉住旧主版本 |
| 次 | 向后兼容的新功能 | 不改代码即可升级 |
| 补丁 | 修 bug，接口不变 | 不改代码即可升级 |

补丁应同时向后和向前兼容：客户可以在补丁之间来回切，不用改代码。主版本号应出现在库文件名里（`libfoo.so.2`、`foo2.dll`），这样不兼容库可以和旧库并存。

提供编译期宏和运行时查询函数，让客户能检查「我正在链的是哪一版」。预发布可用 `1.0.0a` / `1.0.0b`，但对外契约仍以数字三位为主，避免比大小变成一门学问。

### 8.3 兼容性是分层的，承诺必须写进发版说明

「向后兼容」太含糊。书里拆成几层，开发时要能指出你保证的是哪一层：

| 类型 | 含义 | 典型破坏 |
|------|------|----------|
| 功能兼容 | 第 N+1 版运行时行为与第 N 版一致 | 修了一个客户已经依赖的 bug；默默改默认值、精度、错误码 |
| 源代码兼容 | 旧代码不改即可用新头文件重编 | 改签名、把可选参数改成必选、给客户必须实现的基类加纯虚函数 |
| 二进制兼容 | 旧 `.o`/可执行文件不重编也能链新库 | 改对象布局、虚表顺序、调用约定、导出符号名 |
| 向前兼容 | 用新 API 写的代码能在旧库上降级运行 | 新必选参数、新必选虚函数 |
| 协议/文件兼容 | 新旧进程、新旧文件能互读 | 改包格式却不升版本字段 |

功能兼容几乎做不到 100%：修崩溃 bug 就会改变「传入空指针会不会炸」的行为。这不一定是坏事，但要意识到：那也是行为变化，应写进发布说明。纯性能改进、结果不变，则是干净的功能兼容。

源码兼容比二进制宽松。给函数末尾加**带默认值**的新参数，旧源码往往仍能编过；但函数类型（函数指针）变了，二进制通常已经不兼容。

二进制兼容是 C++ 的深水区。Pimpl 是主要工具：变化关在 `.cpp` 里。纯 C API 更容易保持二进制兼容，因为没有继承、重载、默认参数、异常、模板。一条实用策略：内部用 C++ 实现，边界用 C 包装。若必须破二进制兼容，换库名（`zlib.dll` → `zlib1.dll`）让新旧并存。

向前兼容很难保证——你无法预知未来。但在 **1.0 发布之前** 值得做：预留参数、用不透明类型而不是把 `float` 钉死在签名上、能数据驱动就不要把每个字段做成一个函数。1.0 一旦发出，这些空间就用完了。

### 8.4 哪些变更安全，哪些是雷

**通常安全（次版本）：** 新类、新自由函数、新的非虚方法、给枚举加值（若客户没有写「穷尽所有值」的代码）。

**危险：**

- 给客户必须实现的抽象基类**新增纯虚函数** → 旧派生类变成抽象类，无法编译。应变通：新方法提供默认空实现，或把新能力放到新接口类。
- 改虚函数顺序或签名 → 破 ABI。
- 在公共类里加非静态数据成员 → 对象大小改变。Pimpl 可避免。
- 改 `enum` 数值、改默认参数的值 → 源码能编过，行为变了。
- 把 `typedef` 背后的真实类型换掉。
- 内联函数改实现 → 已编译进客户二进制的是旧代码。

**弃用路径：** 标记 deprecated → 编译警告（最好每个调用点只警告一次，不要刷屏）→ 至少一个主版本后再删除。删除等于升主版本，并保留旧包可下载。不要「警告两周就删」。

### 8.5 分支与审查是工程机制，不是流程装饰

主干持续开发；每个已发布主/次版本可拉维护分支打补丁；紧急热修复从发布标签拉出，修完并回主干。小团队可以简化，但不能在「已发布契约」上直接改含义。

两种审查互补：

- **预发布审查：** 发版前集中看本周期全部公共接口 diff。
- **预提交审查：** 改公共头文件必须先批准再合入。

源码能编过 ≠ 可以发给客户。审查要回答的是：旧客户升上来会不会 silently 做错事。

## 1.10 文档、测试、脚本、插件：把契约说清，并打开扩展面

### 9.1 文档补的是头文件说不出的行为

头文件告诉编译器名字和类型。下列内容若不写，接口定义就不完整：

- 每个调用做什么、前置条件、错误与边界；
- 线程安全（可重入？实例级锁？全局锁？）；
- 所有权（谁分配、谁释放、能否持有返回的指针）；
- 性能承诺（若有：复杂度、是否阻塞、是否分配）；
- 版本与兼容性承诺；
- 示例：简单任务的最短代码。示例比长文更能教会可发现性。

Doxygen 一类工具从注释生成参考手册，适合作为「每个符号的契约」。另外还要有：概述/教程、发布说明（行为变化必须出现在这里）。注释写在头文件里，和声明一起演进；只写在 wiki 里的契约会和代码分叉。

### 9.2 测试锁住的是客户行为，不是你的实现偏好

API 测试和最终用户 GUI 测试不同：没有可点的按钮，自动化必须写成调用代码。分类仍有用：

- **黑盒 / 契约测试：** 只根据文档和公共头文件写。这是「客户会怎么用」的替身，也是兼容性的网。换实现、重构 Pimpl、优化算法，这套测试应仍然绿。
- **白盒：** 看源码，覆盖分支。补黑盒覆盖不到的内部风险，但不要把内部函数变成客户契约。
- **集成：** 模块之间、与真实依赖之间。

TDD 对 API 特别合适：先写「客户代码」，再实现。写不顺的测试往往暴露了签名不易用。测试性本身是设计属性——满地单例、隐藏全局、无法注入依赖的 API，测起来会逼你去 friend 内部，那是设计在报警。

回归测试的意义在第 1 章已经出现：你对实现做重大修改时，若有一套证明所需行为未变的用例，才有信心不让客户程序崩溃。

### 9.3 脚本绑定：第二客户群体

用 Boost.Python、SWIG 等把 C++ API 暴露给 Python/Ruby 等。绑定不是「多一个语言」，而是多一类客户，他们往往更不能承受 ABI 细节和手动内存。含义：

- 公共对象模型必须足够干净，否则绑定会放大每个瑕疵；
- 所有权、错误（异常 vs 错误码）、线程模型要先在 C++ 层一致，再映射；
- 你现在多维护一条兼容性表面。核心仍应最小；绑定层可以提供更脚本化的便利 API。

### 9.4 插件：用稳定的小核心换无限的扩展

插件让客户在不改你核心、不重发整个应用的情况下加能力。书中概括的收益：更通用、能催生社区、更新粒度小、核心可以稳定下来靠插件继续演化、内部功能也可以当插件发（自己吃自己的狗粮，如 GIMP）。

代价是：必须有稳定的插件 ABI（因此常见纯 C）、加载/卸载生命周期、版本协商、失败隔离。这是 OCP 在进程边界上的实现：核心对修改封闭，对插件开放。

扩展不一定走插件。继承和模板是进程内扩展；插件是进程外/加载时扩展。选你真正需要的那一层，不要三层一起上。

## 1.11 把全书收成一张决策图

```text
这是不是会有第二客户（含未来的自己）？
    否 → 按模块写好即可，不必当产品级 API
    是 ↓
领域模型是否只表达「做什么」？
    否 → 先改名字和对象，再写实现
    是 ↓
公共头文件里有没有布局、平台#ifdef、内部类、inline 实现？
    有 → 藏进 .cpp / Pimpl / HasXxx()
    无 ↓
每个公共符号是否都有真实用例？虚函数是否都愿意当继承契约？
    否 → 删掉或移到便利层
    是 ↓
签名能否让编译器挡住常见误用？命名和参数顺序是否全库一致？
    否 → 枚举/包装类型/unique_ptr/成对术语
    是 ↓
跨 .so/.dll 吗？
    是 → C 边界或 C++ + Pimpl；模板不要直接导出
    否 → 对象模型可以更「C++」
需要客户扩展？
    算法、可重编 → 模板/策略
    运行时加载 → 工厂注册或插件
    暂时不需要 → 不要预留空架构
发版？
    只加 → 次版本
    改行为/布局/删符号 → 主版本 + 弃用期
    任何情况 → 文档写清行为，契约测试必须绿
```

日常开发 90% 的决策仍落在第 2、4、6、8 章对应的那些问题上。其余章节是这些原则在特定场景下的展开。

## 1.12 走一遍：把原则用在一个小接口上

下面用一个「会话日志记录器」演示设计过程。需求很普通：应用要记下带时间戳的事件，可写到文件，以后可能写到网络，客户是其他 C++ 模块，库会以共享库形式发版。

### 11.1 分析：客户真正要完成的任务

用例只有三条：

1. 打开一个记录器，指定输出位置；
2. 写入一条事件（级别 + 文本）；
3. 关闭（进程结束也应安全释放）。

非目标：自己做日志检索、自己画 UI、暴露 fd。没有用例的能力，这一版不做。

### 11.2 坏的第一稿（看起来「很完整」）

```cpp
class Logger {
public:
    FILE* file;
    int socket;
    bool use_udp;
#ifdef _WIN32
    HANDLE win_handle;
#endif
    void OpenFile(const char* path);
    void Connect(const char* host, int port);
    int GetFd() const;
    void WriteRaw(const char* buf, int n);
    void Log(int level, const char* msg, bool flush, bool with_time);
    void Rotate();
    void SetBufferSize(int n);
};
```

对照六条，几乎全中：

- 模型是文件和套接字，不是「记录事件」；
- 字段公有，平台 `#ifdef` 出现在头文件；
- `GetFd` / `WriteRaw` / `Rotate` 没有用例却成了承诺；
- 两个 `bool` 相邻，必被抄反；
- `Log` 同时管级别、刷新、时间戳，非正交；
- 客户一旦用了 `GetFd`，你再也无法改成无 fd 的实现。

### 11.3 按原则收干净

```cpp
#pragma once
#include <memory>
#include <string>

namespace acme {

enum class LogLevel { Info, Warn, Error };

class Logger {
public:
    static std::unique_ptr<Logger> OpenFile(const std::string& path);
    // 以后加 OpenNetwork(...) 是次版本；客户现有代码不用动

    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
    ~Logger();

    void Log(LogLevel level, const std::string& message);

private:
    class Impl;
    explicit Logger(std::unique_ptr<Impl> impl);
    std::unique_ptr<Impl> impl_;
};

}  // namespace acme
```

选择的理由：

| 决策 | 服务的原则 |
|------|------------|
| 名字是 `Logger`/`Log`，没有 fd | 领域模型 |
| Pimpl + 私有构造 | 隐藏、ABI、编译隔离 |
| 工厂 `OpenFile` 返回 `unique_ptr` | 构造可失败、所有权清晰、不易误用 |
| 禁止拷贝 | 两个对象写同一文件会破坏不变量 |
| `LogLevel` 枚举而不是 `int`+`bool` | 不易误用、一致 |
| 刷新和时间戳不暴露 | 最小；它们是实现策略，可在 `.cpp` 里固定或以后加 `SetOption` |
| 没有 `GetFd` | 正交、可换实现 |
| 命名空间 | 不污染客户 |

网络后端这一版故意没有。等真正有客户要，再加 `OpenNetwork`——这是次版本，旧客户无感。若第一天就做「可扩展后端架构」却没有第二后端，就是过度通用。

### 11.4 错误策略和文档（契约的另一半）

全库选定一种：例如工厂失败返回空指针，`Log` 在已关闭或磁盘满时写失败计数但不抛（嵌入式场景），或统一抛 `std::system_error`。选定后写在头文件注释里，并加两条契约测试：

- 打开合法路径能写下一条 Info；
- 打开非法路径得到空指针（或规定的异常），且不泄漏。

以后把文件实现换成带缓冲、或换成网络，这两条测试应仍然成立。它们锁的是客户行为，不是 `fwrite` 还是 `WriteFile`。

### 11.5 发版之后怎样演进

- 加 `OpenNetwork`、加 `LogLevel::Debug`：次版本。
- 给 `Log` 增加可选结构化字段：不要改成第三个 `bool`；可以新重载 `Log(level, message, const Fields&)`，或一开始就把扩展点做成数据驱动的 `Fields`。旧 `Log(level, message)` 保持不动。
- 把 `Log` 改成虚函数并指望客户继承：通常是错的。客户扩展输出方式，应走新的工厂或插件，而不是继承 `Logger`。
- 发现 `Log` 默认带时间戳让某客户无法忍受：不要改默认行为（功能不兼容）。加新方法或选项，旧默认保持。
- 必须改布局：`Impl` 内部改，主版本号不必动（二进制布局未变）。若当初没做 Pimpl、字段就在公共类里，加一个 `int` 就要升主版本或逼所有客户重编。

这个小例子里没有新语法。它演示的是：原则会主动否决「看起来完整」的第一稿，并把你推向一个更小、更稳、更能加功能的表面。
